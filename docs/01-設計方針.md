### ロードマップ変更の提案（S2でふくちゃん判断）
- **L2「ローカルWebアプリ自作」→「既存ツール導入検証」に置き換え**（claude-view / Agent View 試用）。自作リソースは L1（静的ダッシュボード）と L3（業務ダッシュボード統合）に集中
- 発展候補: Agent SDK の `tag_session`/`rename_session` で検出した採番をセッション本体に書き戻す → 公式 `/resume` ピッカーや既存ビューアにも案件名が出る（自作地図と既存ツールの橋渡し）

## jsonl・メタデータ構造の知見（実地調査）

- レコード type: `user` / `assistant` / `system` / `attachment` / `queue-operation` / `file-history-snapshot` / `ai-title` / `last-prompt`
- **`ai-title`** = Claude Code が付けるセッションタイトル。採番合言葉がそのまま入ることが多く**マッピングの1級ソース**（ただし英語化・言い換えされることあり）
- ユーザー発話は `<ide_opened_file>` 等の環境タグと同居 → タグ除去・`isMeta`/`isSidechain` 除外が必須
- サブエージェント記録: `projects/<WS>/<session-id>/subagents/agent-*.jsonl`（照準③のデータ源）
- 稼働中レジストリ: `~/.claude/sessions/<pid>.json`（pid/sessionId/cwd/startedAt）→ 照準②は「これ×PID生存確認」で実装可能
- `history.jsonl` は直近分のみ（89行）＝完全アーカイブではない。正は projects 配下の jsonl
- トークン: assistant レコードの `message.usage`（input/output_tokens）

## アーキテクチャ（L0で確立・L1でも維持）

```
config.local.json（個人設定: 採番正規表現・案件別名・ヒント）← 汎用コアから分離
        │
claude_sv/ （汎用コア）
  parser.py   … jsonlストリームパース（読み取り専用・不完全行スキップ）
  scan.py     … 全WS走査＋mtime/size差分キャッシュ
  mapping.py  … 採番マッチ＋別名解決＋タイトル/WSヒント
        │
l0_report.py … Markdownレポート（L1では claude_dashboard_gen.py → HTML に発展）
```

- マッピング精度の設計判断:
  - パターンは**文頭アンカー**（`^\W{0,8}`）＝会話中に偶然出る「S6 開始」の誤マッチを排除（precision優先・取りこぼしは未分類一覧から別名追加で回収）
  - 別名解決は「完全一致 → **末尾一致優先** → 最長部分一致」（「KANADEMONO ウエルカムDM」→ ウェルカムDM に正しく解決）
  - 判定順: 採番パターン → タイトルヒント（業務ハブ等） → ワークスペースヒント（専用リポジトリ）
- キャッシュ実績: 初回全パース 267セッション/686MB ≈ 2分 → 差分再実行は数秒（変更ファイルのみ）

## L1 技術方針

- **Python 静的生成**（`dashboard_gen.py` と同型・L3統合前提。ローカルWebアプリはL2判断まで作らない）
- 成果物: `claude_dashboard_gen.py` → HTML 1枚（案件×セッション地図・日別稼働ヒートマップ・案件別トークン）
- 業務ダッシュボードとの統合は「JSON中間出力 → dashboard_gen.py 側で読む」を想定（生成物にトランスクリプト本文を含めない＝機密最小化）

## L0 実績・既知の限界

- マッチ率 54%（143/267・22案件）。未分類124本の主因は採番運用開始（7月）前の5〜6月セッション＝ベストエフォートで想定内
- `/clear` 等で同一S番号が複数ファイルに分かれる（例: TOPPAN S2×2）→ L1では「案件×S番号」で束ねて表示
- ai-title の英語化（"Life S3 start"）→ パターンに `start|スタート` を追加済み。今後も未分類一覧を見て別名・パターンを育てる運用
